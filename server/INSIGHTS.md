## Codebase Patterns
- **2026-08-01** — Adding a field to `PrMeta` also changes `GET /pulls/:id`, because `PrDetail = PrMeta.extend({...})`. Declare list-only aggregates with `.nullish()` (as `score` does) and both detail branches keep compiling untouched; a plain `.nullable()` would force you to fill the GitHub-refresh AND offline-fallback literals — `server/src/vendor/shared/contracts/platform.ts:172`
- **2026-08-01** — `enqueue()` returns `done`, which REJECTS on failure, but every call site keeps only `job.id` — that floating rejection used to kill the API process via Node's default `unhandledRejection`. A no-op `done.catch()` now marks it observed; if you add a new job kind, the failure is still readable from the `jobs` row (status/error), not from `done` — `server/src/platform/jobs.ts:108`
- **2026-08-01** — RunStats.cost_usd (Run Trace drawer COST stat) was intentionally excluded in the first cost pass — added later. Adding a required field to RunStats/RunTrace breaks any `.parse()` call in tests that hand-builds the object, e.g. `server/test/contracts.test.ts:160` — both vendor copies AND every test fixture need the field, not just the schema.
- **2026-08-02** — Per-PR severity rollup pattern: `findingsByPr()` mirrors `costByPr()` immediately above it — one `inArray` join (`findings` has no `pr_id`, join through `reviews`), filtered to `kind: 'review'` + `isNull(dismissedAt)`, grouped in JS, tallied with `rollupSeverities()` — `server/src/modules/pulls/routes.ts:353`
- **2026-08-04** — `skills.pull_rate` (SkillCard/StatsTab "71% pull") has no precedent elsewhere in the codebase (unlike `accept_rate`, which reuses the `accepted/(accepted+dismissed)` definition from `AgentPerfRow`/`observability.ts`) — defined as `run_skills` rows for the skill ÷ `agent_runs` by agents CURRENTLY linked to it; `agent_skills` has no history so this is evaluated against today's links, not the links at each historical run — `server/src/modules/skills/repository.ts:154`
- **2026-08-04** — Cost-split math for Stats (`agent_runs.cost_usd / findings_count` per finding, grouped by category) is deliberately pulled out of the repository query into a pure `apportionCostByCategory()` so it is unit-testable without Postgres, instead of doing the division in SQL — `server/src/modules/skills/stats.ts:33`, `server/test/skills-stats.test.ts`
- **2026-08-04** — Refines the pull_rate entry above: user testing showed a freshly-linked skill with ONE clean run reported pull_rate=20% instead of ~100%, because the denominator counted an agent's ENTIRE run history (including runs from before the skill even existed). Fixed by joining `agent_runs.ranAt >= skills.createdAt` as a floor — still approximate (a skill can be linked well after creation) but no longer counts runs the skill couldn't possibly have been attached to — `server/src/modules/skills/repository.ts:282`, `server/test/skills-stats.it.test.ts` ("pull_rate ignores an agent run that predates the skill")
- **2026-08-11** — `pnpm typecheck` (`tsc --noEmit -p tsconfig.json`) never typechecks `server/test/**` — `tsconfig.json:50` `include` is `["src/**/*.ts"]` only, so a green `pnpm typecheck` proves nothing about test-file types (path aliases like `@devdigest/shared` show as `TS2307` in an IDE for any file under `test/`). `tsconfig.test.json` (new) extends the base config with `test/**/*.ts` added to `include`, purely so editors resolve `test/` correctly — it is deliberately NOT wired into `pnpm typecheck`/CI, because doing so immediately surfaces 15 pre-existing latent type errors across 6 unrelated files (`adapters.test.ts`, `agents-versions.it.test.ts`, `intent-classifier.test.ts`, `prompt-callers.test.ts`, `repo-intel-facade-degraded.test.ts`) that predate this discovery.

## Tool & Library Notes
- **2026-08-01** — drizzle types `sum()` as `SQL<string | null>` (numeric semantics) even over a `doublePrecision` column, where pg actually returns a JS number — coerce with `Number()` and guard `Number.isFinite` rather than trusting either type — `server/src/modules/pulls/routes.ts:345`
- **2026-08-03** — fflate's `unzipSync(buf, { filter })` calls the filter per entry BEFORE inflating, with `file.originalSize` already available from the zip header — reject by extension/size/path/count inside the filter and nothing unsafe is ever decompressed (grep-provable: no `node:fs` import needed). Track a running `seen` counter in the filter closure to cap total entries, since fflate gives no index/count parameter — `server/src/adapters/archive/fflate.ts:38`
- **2026-08-03** — OpenRouter/DeepSeek-reported `usage.prompt_tokens` (→ `stats.tokens_in`) is NOT monotonic in the text actually sent: two back-to-back calls sharing most of the same prefix (same diff, same base system prompt, differing only by an appended skills block) can report FEWER prompt tokens on the longer call — almost certainly provider-side prompt-caching credit, not a bug in `assemblePrompt` (which is a deterministic string join, verified by `skills-prompt-blocks.test.ts`). Do not use `tokens_in` deltas as a signal for "did X reach the prompt" in any experiment/eval — use `prompt_assembly.<field> != null` instead, which is exact — `docs/experiments/skills/RESULTS.md`

## Recurring Errors & Fixes
- **2026-08-23** — `pnpm db:generate` failed with `Cannot find module './_shared.js'` (CJS require stack rooted at `db/schema/reviews.ts`) for ANY schema change, not just the one being made — `drizzle-kit generate` (0.30.6) loads `db/schema.ts` via a plain CJS `require()` and does NOT do TS `moduleResolution: Bundler`-style `.js`→`.ts` remapping the way `tsc`/webstorm do. `db/schema/reviews.ts` was the only schema file importing sibling modules WITH a `.js` extension (`./_shared.js`, `./core.js`); every other schema file (`core.ts`, `pulls.ts`, …) imports extensionless. Fixed by dropping the extension to match the sibling convention — `server/src/db/schema/reviews.ts:3-4`. If `db:generate` ever throws `MODULE_NOT_FOUND` again, check for a stray `.js` extension in a `db/schema/*.ts` relative import before assuming the DB/config is broken.
- **2026-08-23** — `z.object({...}).default({})` does NOT rescue a body-less POST from 422 under `fastify-type-provider-zod` — a request injected/fetched with no payload arrives as `body === null`, not `undefined`, and Zod's `.default()` only substitutes on `undefined`. Use `z.preprocess((v) => v ?? {}, z.object({...}))` instead, which normalizes both `null` and `undefined` before the object schema runs — `server/src/modules/reviews/routes.ts` (`BriefRequest`). Confirmed via the actual validation error body: `{"expected":"object","received":"null"}`.
- **2026-08-01** — `PostgresError: deadlock detected` (40P01) on `relation "references"` = two repo-intel index jobs running for the SAME repo at once; `JobRunner` concurrency is 3 and nothing serializes them, and both DELETE-then-INSERT the repo's reference rows — `server/src/modules/repo-intel/repository.ts:262`
- **2026-08-03** — `waitForPrRuns`'s default 10s `timeoutMs` (`test/helpers/runs.ts:19`) is too tight for a mock-LLM run when the FULL `vitest run` suite executes — ~15-20 concurrent Testcontainers-backed `.it.test.ts` files contend for CPU and a single review run that takes <1s in isolation can take several seconds under load. A test calling `waitForPrRuns` more than once for the SAME PR (e.g. "toggle then re-run") must also pass `expected: <prior terminal count> + 1`, not a bare `expected: 1` — the helper counts ALL terminal runs for the PR, so a bare 1 resolves immediately against the first run's already-terminal row and races the second — `server/test/review-skills.it.test.ts`
- **2026-08-11** — A new `.it.test.ts` file showing "skipped" in the full `pnpm exec vitest run .it.test` pass does not mean Docker is unavailable or the test is broken — `dockerAvailable()` in `test/helpers/pg.ts:1` caches a 5s `docker info` timeout per worker, which can false-negative under parallel load. Re-run the file in isolation (`pnpm exec vitest run test/<file>.it.test.ts`) before concluding anything.
  Observed with `test/smart-diff.it.test.ts` — skipped in the full run, 3/3 passed in isolation against real Postgres via Testcontainers.

## Decisions
- **2026-08-01** — `agent_runs.cost_usd` is nullable and MUST stay null (never 0) on failed/cancelled/pre-work-failure runs: the UI reads null as "unknown" (dash) and 0 as "free" — `server/src/modules/reviews/run-executor.ts:82`
- **2026-08-02** — `status.ts`'s local `SeverityCounts` interface was replaced with `export type { SeverityCounts }` re-exported from `@devdigest/shared` instead of duplicating the shape — `rollupSeverities()`'s return type is structurally identical so no callers needed changes — `server/src/modules/pulls/status.ts:16`
- **2026-08-03** — `AgentsRepository.setSkills`/`linkSkill` validate a skill's workspace by a plain `select` join against `t.skills` inside the same repository, NOT via a `SkillsRepository` instance — the skills spec explicitly forbids adding `container.skillsRepo` since no other module needs it; cross-workspace validation belongs on the write path (the read path `linkedSkills(agentId)` stays unscoped, matching the signature `run-executor.ts` already calls it with) — `server/src/modules/agents/repository.ts:207`
- **2026-08-04** — Reverses the 2026-08-03 "no container.skillsRepo" decision: the Extension (Stats/Versions) added a second consumer (`ReviewRunExecutor` persisting `run_skills`), so `container.skillsRepo` now exists, mirroring `agentsRepo` exactly — `server/src/platform/container.ts:109`
- **2026-08-23** — PR Brief (SPEC-03) AC-7 asks `collectBriefContextDocs` to reuse `resolveContextDocs()`/`readContextDocsForRun()` for "relevant specs", but those are AGENT-scoped (`ContextDocsRepository.listForAgent(agentId)`) and brief generation runs without an agent — there is no workspace- or repo-level context-docs list anywhere in the schema. Resolved by unioning the OWN attachments of every ENABLED agent in the workspace (`container.agentsRepo.listEnabled(workspaceId)` → `listForAgent` per agent → concatenated), then deduping through the SAME pure `resolveContextDocs({ skills: [], agentDocs })` the run-executor uses (first occurrence wins) before reading via `readContextDocsForRun` — `server/src/modules/reviews/brief/sources.ts` (`collectBriefContextDocs`). If a narrower scope (one specific agent, or none at all) is wanted later, this is the one function to change; nothing else in the brief pipeline depends on the scope decision.
- **2026-08-23** — `PrBrief.risks` changed shape: it used to be a `Risks` wrapper object (`{ risks: Risk[] }`); it is now the plain `Risk[]` inherited from `BriefCore` (`PrBrief = BriefCore.extend({ intent, blast, history? })`). Confirmed zero consumers before the change via `grep -rn "PrBrief\b" server/ client/` (only `server/test/contracts.test.ts`'s `Risks.parse()` fixture and a `client/src/lib/types.ts` type-only re-export existed — neither broke).
- **2026-08-23** — `client/messages/en/brief.json` remains an orphaned i18n namespace after this feature — `PrBriefCard` deliberately uses the existing `prReview` namespace (new `brief.*` keys added to `client/messages/en/prReview.json`), mirroring `IntentCard`'s `intent.*` keys, so the card needs only ONE namespace registered in a test's `NextIntlClientProvider`. `brief.json` was not touched or deleted — do not assume it's dead code without checking whether some future card was meant to consume it.
