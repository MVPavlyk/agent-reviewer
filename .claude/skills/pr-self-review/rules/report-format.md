# Report format

Written to `.devdigest/self-review/<branch-slug>-<UTC yyyymmdd-HHMMSS>.md`, and
the same content overwrites `.devdigest/self-review/latest.md`. Branch slug is
the branch name with `/` replaced by `-` (`feat/l-02` → `feat-l-02`).

**Precondition — check before writing anything:** confirm
`.devdigest/self-review/` is covered by `.gitignore` (it should already be,
next to `.devdigest/cache/`). If it isn't, stop and tell the user instead of
writing an untracked report into the very diff being reviewed — otherwise
run N+1 reviews run N's own report file.

**Rotation:** after writing, keep at most the 10 most recent timestamped
reports for the current branch slug and delete older ones. Never delete
`latest.md`. This is housekeeping, not an archive — a stale report proves
nothing about the current tree (see the freshness rule in `SKILL.md`).

## Required header field — the freshness hash

The first line of the report body (right after the `##` header, before the
summary line) must be:

```
_Tree: <hash>_
```

`<hash>` is computed from the exact inputs used for diff collection in Phase 0
— e.g. a hash of `git diff --name-status main...HEAD` concatenated with
`git status --porcelain`. Any deterministic hash of those two outputs is fine;
what matters is that re-running the same two commands on an unchanged tree
reproduces the same hash, and any tree change (even to a file already in the
diff) changes it. This is what the gate in `SKILL.md` compares against before
trusting an existing `latest.md`.

## Body template

Mirrors `reviewer-core/src/output/to-review.ts`'s `composeBody` shape — emoji,
the `N critical · N warning · N suggestion` summary line, and the
`- {emoji} **{title}** ({severity}, {category}) — \`file:start-end\`` finding
line — so a self-review reads like the product's own review, plus a routing
preamble the product review doesn't need.

```markdown
## PR Self Review — Changes requested

_Tree: a3f9e21c_

**7 findings** · 1 critical · 4 warning · 2 suggestion

**Verdict:** `request_changes` — merge blocked until the CRITICAL is fixed or waived.

### Scope
- Branch `feat/l-02` vs `main` · 21 files (14 modified, 7 untracked)
- Excluded from review: `server/src/db/migrations/**` (generated, 3 files)
- Routed skills: fastify-best-practices, onion-architecture, zod, security,
  drizzle-orm-patterns, postgresql-table-design, react-best-practices, frontend-architecture
- Not run under the 8-skill cap: typescript-expert
- Reviewed without a domain skill: CLAUDE.md, .claude/skills/README.md

### Findings
- 🔴 **<title>** (critical, bug) — `server/src/modules/pulls/service.ts:41-48`
  - <rationale — the concrete mechanism, not "might be an issue">
  - _Suggestion:_ <fix>
- 🟡 **<title>** (warning, style) — `client/src/lib/hooks/index.ts:12`
  - <rationale>
- 🔵 **<title>** (suggestion, test) — `...`
  - <rationale>

### Blockers
1. `server/src/modules/pulls/service.ts:41` — <one-line summary of the CRITICAL>

_Generated by /pr-self-review. Not a substitute for the DevDigest PR review._
```

The header line switches by verdict, exactly like `composeBody`:

- `request_changes` → `## PR Self Review — Changes requested`
- `comment` → `## PR Self Review`
- `approve` → `## PR Self Review — Approved ✅`

When findings is empty: `_No findings. Looks good._` instead of a `### Findings`
section, and no `### Blockers` section.

### `### Waived` section (appended only when a waiver was granted)

```markdown
### Waived
- **<finding title>** (`file:line`) — waived by user on 2026-08-02: "push
  anyway, I accept the risk"
```

One entry per waived finding, in the user's own words, with the date. Append
this to `latest.md` in place — don't regenerate the whole report for a waiver.
