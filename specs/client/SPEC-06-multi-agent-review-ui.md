# Spec: Multi-Agent Review — Configure run, пікер агентів на сторінці PR і сторінка результатів (Columns/Tabs)
Spec ID: SPEC-06
Status: draft
Supersedes: —
Depends on: [`specs/server/SPEC-05-multi-agent-run-server.md`](../server/SPEC-05-multi-agent-run-server.md)

## Affected packages
- **`client/` (@devdigest/web)** — первинний пакет: сторінка `Multi-Agent Review`
  (`Configure run` + результати з перемикачем Columns/Tabs), новий пікер агентів на
  сторінці PR (замінює `RunReviewDropdown`), хуки `lib/hooks/*` для мультизапуску.
- **`server/`** — усі дані з API зі SPEC-05; нового серверного контракту тут не вводимо.
- **`vendor/shared`** — типи `MultiAgentRun`/`AgentColumn`/`Conflict`/`ConflictTake` уже
  є в `client/src/vendor/shared/contracts/observability.ts`; за потреби дзеркалимо з
  server лише те, що треба UI (правило drift з кореневого `CLAUDE.md`).
- **OUT of scope:** Compose Review drawer (курує знахідки перед публікацією — інший
  потік), `ci/`, `agent-runner/`.

## Проблема й користувач
**Хто:** рев'юер у Studio UI, що хоче обрати кілька агентів, прогнати їх паралельно по
PR і порівняти знахідки.

**Проблема:** сьогодні на сторінці PR є `RunReviewDropdown` («один або всі») —
`client/src/app/repos/[repoId]/pulls/[number]/_components/RunReviewDropdown/`. Немає
екрана, де можна свідомо обрати набір агентів з орієнтиром «час·вартість», побачити
попередню оцінку fan-out і порівняти результати колонками/вкладками з блоком «де агенти
не згодні». Попередньої оцінки вартості в продукті ще немає взагалі — це нова механіка.

## Goals / Non-goals

**Goals:**
- G-1. Сторінка `Multi-Agent Review › Configure run`: крок 1 — вибір PR; крок 2 —
  чекбокси агентів з поагентним `time·cost` орієнтиром; кнопка `Run multi-agent
  review (N)`; жива pre-run оцінка `≈ MAXs · $SUM · parallel fan-out`.
- G-2. Швидкий пікер «Pick agents to run» на сторінці PR, що замінює `RunReviewDropdown`
  й передає обраний набір у мультизапуск.
- G-3. Сторінка результатів `Multi-Agent Review › #<pr>` з одним перемикачем режимів
  над тими самими даними прогону: **Columns** і **Tabs + detail**.
- G-4. Блок «Where agents disagree» в обох режимах: групи по одному місцю коду, вердикт
  кожного агента (в т.ч. «did not flag»), тумблер «Show only conflicts».
- G-5. Дії над знахідкою в detail: **Accept**/**Dismiss** — реальні (персист через
  бекенд), **Learn**/**Turn into eval case**/**Reply to author** — UI-заглушки (no-op + TODO).
- G-6. Повний набір станів: empty (PR не обрано), loading/live (прогін триває), done,
  збій агента, часткова оцінка.
- G-7. Живі статуси в заголовках колонок і `View trace` з кожної колонки/вкладки через
  наявні SSE + `RunTraceDrawer` + `LiveLogStream`.

**Non-goals:**
- N-1. Будь-яке серверне обчислення (мультизапуск, групи, оцінка) — це SPEC-05; клієнт
  довіряє отриманому.
- N-2. Реалізація бекендів Learn / Turn into eval case / Reply to author — лише заглушки
  з TODO, що посилаються на майбутню роботу (Memory, L06 evals).
- N-3. Compose Review drawer.
- N-4. Новий скоринг: кільце-скор у заголовках колонок/вкладок — це наявний
  `agent_runs.score`; не вигадуємо новий механізм.
- N-5. Зміна SSE/RunTrace/LiveLog-примітивів — повторно використовуємо як є.
- N-6. Перерахунок `risk`/severity/оцінки на клієнті.

## User stories
- US-1: Як рев'юер, я хочу на сторінці Configure run обрати PR і набір агентів з
  орієнтиром час·вартість, щоб свідомо сформувати прогін.
- US-2: Як рев'юер, я хочу бачити живу pre-run оцінку `≈ час · вартість · parallel
  fan-out`, що оновлюється з кожним чекбоксом, щоб розуміти ціну до запуску.
- US-3: Як рев'юер, я хочу швидкий пікер агентів прямо на сторінці PR замість «один або
  всі», щоб запускати мультизапуск без переходу на окремий екран.
- US-4: Як рев'юер, я хочу перемикати результат між Columns і Tabs над тими самими
  даними, щоб дивитись або зведення пліч-о-пліч, або деталі одного агента.
- US-5: Як рев'юер, я хочу блок «де агенти не згодні» з тумблером «тільки конфлікти»,
  щоб дублі не набридали, а розбіжності було видно.
- US-6: Як рев'юер, я хочу Accept/Dismiss знахідки з персистом стану й `View trace`
  кожного агента, щоб діяти по знахідці й перевіряти, як агент до неї дійшов.

## Acceptance criteria (EARS)

### Configure run — вибір PR і агентів
- AC-1: КОЛИ користувач відкриває `Configure run` без обраного PR, система повинна
  показати empty-state крок 2 («Pick a pull request first» + підказка), а список
  агентів не рендерити.
- AC-2: ПОКИ PR не обрано, система повинна тримати кнопку `Run multi-agent review (N)`
  вимкненою й не показувати рядок оцінки.
- AC-3: КОЛИ користувач обирає PR у кроці 1, система повинна відрендерити список агентів
  (чекбокс, іконка/акцент, назва, one-line blurb, right-aligned `time·cost` з історії).
- AC-4: КОЛИ користувач тисне `Select all`, система повинна позначити всі агенти й
  оновити лічильник `(N)` та оцінку.
- AC-5: КОЛИ користувач перемикає будь-який чекбокс агента, система повинна наживо
  оновити лічильник `(N)` у кнопці й агрегатну оцінку.
- AC-6: Система повинна відображати pre-run оцінку як `≈ <MAX часів обраних>s ·
  $<SUM вартостей обраних> · parallel fan-out`, де MAX/SUM беруться з даних SPEC-05.
- AC-7: ЯКЩО в обраного агента немає історії, ТОДІ система повинна показати для нього
  `—` у полі `time·cost` і виключити його з агрегату, позначивши оцінку як часткову.
- AC-8: ЯКЩО обрано 0 агентів АБО PR не обрано, ТОДІ система повинна тримати кнопку
  запуску вимкненою (запуск не може відбутись без PR і ≥1 агента).
- AC-9: КОЛИ користувач тисне активну `Run multi-agent review (N)`, система повинна
  викликати `POST /pulls/:id/multi-agent-run` з обраним набором і перейти на сторінку
  результатів цього мультизапуску.

### Пікер на сторінці PR
- AC-10: Система повинна додати на сторінці PR пікер «Pick agents to run», що дозволяє
  обрати кілька агентів (не лише «один або всі»), і при цьому **залишити наявний
  `RunReviewDropdown` як швидкий single-агентний шлях поруч** (рішення D-2c). Обидва
  запускають прогін тим самим бекенд-шляхом.
- AC-11: КОЛИ користувач підтверджує вибір у пікері, система повинна запустити
  мультизапуск тим самим шляхом, що й Configure run (`POST /pulls/:id/multi-agent-run`).
- AC-12: ЯКЩО у пікері не обрано жодного агента, ТОДІ система повинна тримати дію
  запуску вимкненою.

### Сторінка результатів — спільний каркас
- AC-13: Система повинна показувати заголовок з бредкрамбом `Multi-Agent Review › #<pr>`,
  кнопкою `Configure run`, підзаголовком `<N> selected agents · parallel`, рядком
  `#<pr> <title>` і meta `<N> agents · fan-out via worktrees · <total>s total · $<cost>`.
- AC-14: Система повинна показувати сегментований перемикач `Columns | Tabs`, що
  перемикає режим над **тими самими** даними прогону (одна сторінка, не два роути).
- AC-15: ПОКИ мультизапуск триває, система повинна показувати живі статуси агентів
  (running/done, стрімінг часу/вартості) через наявний SSE (`GET /runs/:id/events`),
  без повного перезавантаження сторінки.
- AC-16: КОЛИ користувач тисне `View trace` будь-де на сторінці (футер колонки, банер
  вкладки), система повинна відкрити **той самий** `RunTraceDrawer`, що й на сторінці PR,
  для відповідного `run_id` — з усіма його вкладками: **Trace** (Configuration / Stats /
  Prompt assembly / Tool calls / Raw output) і **Live log** (SSE через `useRunEvents` →
  `LiveLogStream`). Компонент перевикористовується, НЕ переписується й НЕ форкається.
- AC-16a: Оскільки `RunTraceDrawer` наразі лежить у `_components/` PR-роуту
  (`client/src/app/repos/[repoId]/pulls/[number]/_components/RunTraceDrawer/`), його
  треба **підняти в спільне розташування** (напр. `client/src/components/RunTraceDrawer/`
  або feature-shared шар), щоб і PR-сторінка, і Multi-Agent Review імпортували одну копію
  (frontend-architecture: спільний між роутами компонент живе в shared-шарі). Наявні
  імпорти й тести PR-роуту оновлюються на новий шлях; поведінка й розмітка не міняються.

### Режим Columns
- AC-17: КОЛИ активний режим Columns, система повинна показати по одній колонці на
  агента з кольоровою верхньою межею акценту агента; заголовок містить іконку+назву,
  кільце-скор (наявний `score`) і `time·cost`.
- AC-18: Кожна колонка повинна перелічувати знахідки агента компактними рядками
  (іконка severity + заголовок + `path:line`) і футер `View trace` (ліворуч) ·
  `<K> findings` (праворуч).
- AC-19: ЯКЩО агент завершився збоєм, ТОДІ його колонка повинна показати стан збою
  (а не порожній список як «0 findings»), лишаючись читомою.

### Режим Tabs + detail
- AC-20: КОЛИ активний режим Tabs, система повинна показати по вкладці на агента
  (іконка + назва + числовий бейдж-скор); активна вкладка має банер-зведення
  (кільце-скор, заголовок, summary, `View trace` + `time·cost`).
- AC-21: Система повинна рендерити знахідки активної вкладки як розгортувані картки:
  іконка severity + заголовок + category-tag chip + `path:line` + confidence-піл
  (`% conf`, зелена крапка при high, амбер при medium — з наявного поля confidence).
- AC-22: КОЛИ користувач розгортає картку знахідки, система повинна показати тіло
  опису, підсекцію `SUGGESTED FIX` і рядок дій.
- AC-23: КОЛИ користувач тисне `Accept` або `Dismiss`, система повинна викликати
  наявний бекенд-екшн (`POST /findings/:id/accept|dismiss`, хук `useFindingAction`) і
  відобразити персистований стан картки (accepted/dismissed-стилізація) після дії.
- AC-24: КОЛИ користувач тисне `Learn`, `Turn into eval case` або `Reply to author`,
  система повинна виконати no-op (жодного бекенд-виклику) з TODO-коментарем на майбутню
  роботу (Memory / L06 evals) — кнопки рендеряться, але не діють.

### Where agents disagree (обидва режими)
- AC-25: Система повинна показувати секцію `WHERE AGENTS DISAGREE` в обох режимах
  (Columns і Tabs), читаючи `conflicts` з відповіді SPEC-05 (обчислені сервером on-read;
  клієнт нічого не групує сам).
- AC-26: Кожна група повинна показувати `path:line` + короткий label теми і 3-колонкову
  сітку (клітинка на агента) з назвою агента, бейджем вердикту (severity або
  **did not flag**) і one-line rationale.
- AC-27: КОЛИ увімкнено тумблер `Show only conflicts`, система повинна показувати лише
  групи, де агенти справді розходяться (≥1 flag + ≥1 did-not-flag, або різні severity),
  ховаючи одностайні групи.
- AC-28: ЯКЩО `conflicts` порожні (мультизапуск ще триває або нема розбіжностей), ТОДІ
  система повинна показати відповідний порожній/очікувальний стан секції, а не зламану сітку.

## Edge cases
- EC-1: PR не обрано → крок 2 схований, кнопка вимкнена, оцінки нема (AC-1, AC-2).
- EC-2: Обрано 0 агентів після зняття всіх галок → кнопка вимкнена, `(0)` (AC-8).
- EC-3: Частина агентів без історії → їхній `time·cost` = `—`, агрегат частковий,
  UI позначає частковість оцінки (AC-7).
- EC-4: Мультизапуск триває, дані приходять поступово → колонки/вкладки показують
  running-статуси, `conflicts` порожні до завершення (AC-15, AC-28).
- EC-5: Один агент завершився збоєм, інші успішні → його колонка/вкладка у стані збою,
  решта нормальні (AC-19).
- EC-6: Знахідка вже Accepted/Dismissed при завантаженні → картка одразу в
  персистованому стані, не «pending» (AC-23).
- EC-7: Мережева/бекенд-помилка `POST /pulls/:id/multi-agent-run` → показати помилку,
  не переходити на порожню сторінку результатів.
- EC-8: Прямий вхід на сторінку результатів неіснуючого мультизапуску → показати
  not-found/empty стан (сервер віддає 404, SPEC-05 AC-17).
- EC-9: Дуже довгий список агентів / довгі blurb-и → список скролиться, картки не ламають
  розмітку.
- EC-10: Перемикання Columns↔Tabs під час активного прогону → режим міняється без
  втрати живого стану (одні й ті самі дані, AC-14).
- EC-11: Агент, що завершився збоєм, не має бути показаний у групі як «did not flag»
  (дані зі SPEC-05 AC-10 це розрізняють) — UI лише відображає те, що прийшло.

## Non-functional requirements
- **Продуктивність:** живі оновлення через наявний SSE-хук (`useRunEvents`) без
  polling; оцінка перераховується локально з уже завантажених даних (без запиту на
  кожен клік чекбокса, окрім першого завантаження оцінок набору).
- **Доступність (a11y):** чекбокси агентів, сегментований перемикач Columns/Tabs і
  тумблер `Show only conflicts` мають доступні мітки/ролі й керуватися з клавіатури;
  колір-акцент агента не єдиний носій інформації (є іконка/текст); confidence і severity
  не передаються лише кольором (є текст/іконка). Дотримуватись наявних патернів
  (напр. явний `aria-label` для severity-пілів, як у нещодавньому фіксі SeverityCounts).
- **Стан/URL:** активний режим (Columns/Tabs), обраний PR і набір агентів у Configure
  run, а також ідентифікатор мультизапуску мають жити в URL (query/route params), щоб
  переживати refresh і бути шеронтими (frontend-architecture: filter/tab state → URL).
- **Розміщення коду:** нова фіча — під route-segment сторінки Multi-Agent Review з
  `_components/` колокацією; доступ до API лише через `lib/hooks/*` → `lib/api.ts`
  (frontend-architecture, client CLAUDE.md). `"use client"` — якнайнижче в дереві.
- **Безпека:** усі дані з бекенду (тексти знахідок/rationale — LLM-генеровані)
  рендеряться як текст (React auto-escaping); `path:line`-посилання й будь-які URL не
  передавати в `href` без перевірки протоколу; жодного `dangerouslySetInnerHTML`.

## Inputs and provenance
- Список PR і агентів (назви, blurb/summary), поагентні `time·cost`, дані мультизапуску
  (колонки, знахідки, конфлікти), стан Accept/Dismiss — усе з API SPEC-05 (+ наявні
  роути reviews). Клієнт — лише споживач; джерело правди на сервері.
- Акцент-кольори агентів: наявні токени продукту, якщо є; інакше — мапа акцентів на
  клієнті (design 01 note). Іконки severity/скор-кільце — наявні UI-примітиви.
- Live-статуси/трейс: наявні SSE (`/runs/:id/events`), `RunTraceDrawer`, `LiveLogStream`.

## Untrusted inputs
- Тексти знахідок, summary, rationale, `SUGGESTED FIX`, назви агентів — LLM-генеровані
  (недовірені): рендерити як екранований текст, не як HTML; інлайн-code-chips — як
  текст у `<code>`, без інтерпретації.
- Будь-які file-path/URL із даних — не вставляти в `href`/`src` без перевірки
  (лише внутрішня навігація до diff/файлу; протокол `javascript:` відкидати).

## Decisions (закриті продукт-овнером)
- **D-2c (RunReviewDropdown):** лишаємо наявний `RunReviewDropdown` як швидкий
  single-агентний шлях; новий мультипікер додається поруч (не заміна). Тести
  RunReviewDropdown не ламати (AC-10).
- **D-trace (сайдбар логів):** кнопка логів на Multi-Agent Review відкриває той самий
  `RunTraceDrawer`, що й PR-сторінка, з усіма вкладками (Configuration / Stats / Prompt
  assembly / Tool calls / Raw output + Live log). Компонент піднімається в спільний шар
  і імпортується обома роутами (AC-16, AC-16a).
- **D-fanout:** «fan-out via worktrees» у meta-рядку — статичний дескриптор (реальна
  worktree-механіка поза межами worktree A).
- **D-history (ОНОВЛЕНО — історія тепер у scope):** глобальна сторінка
  `/multi-agent` показує ІСТОРІЮ мультизапусків (список, найновіші перші), з якого
  можна відкрити будь-який за `multiRunId`. Опційний фільтр `?prId=` звужує список до
  одного PR. Сторінка PR має лінк на останній мультизапуск цього PR. (Раніше історія
  була поза scope — продукт-овнер розширив.)
- **D-estimate:** pre-run оцінка тягнеться з окремого роуту `GET /agents/estimates?ids=…`
  (SPEC-05 D-6) через новий хук `lib/hooks/*`.
