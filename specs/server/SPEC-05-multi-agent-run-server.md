# Spec: Multi-Agent Review — сервіс мультизапуску, роути та крос-агентна група on-read (серверна половина)
Spec ID: SPEC-05
Status: draft
Supersedes: —

## Affected packages
- **`server/` (@devdigest/api)** — первинний пакет: новий сервіс `multi_agent_runs`
  (лінкування окремих `agent_runs` під одним мультизапуском), роути `POST /pulls/:id/multi-agent-run`
  та `GET /pulls/:id/multi-agent` (+ `GET .../:multiRunId`), а також **on-read
  обчислення** крос-агентної групи «Where agents disagree» (без персисту, рішення D-2).
- **`reviewer-core/`** — не змінюється; використовується як є через
  `reviewPullRequest` (паралельне виконання агентів уже існує).
- **`vendor/shared`** — контракти `MultiAgentRun`/`AgentColumn`/`Conflict`/`ConflictTake`
  вже існують у `server/src/vendor/shared/contracts/observability.ts`. Правки
  вносяться **спочатку** сюди, у `client/src/vendor/shared` дзеркалиться лише те, що
  потрібно UI (правило drift з кореневого `CLAUDE.md`).
- **OUT of scope:** `ci/`-движок і `agent-runner/` — не чіпаються (межа worktree A).

## Проблема й користувач
**Хто:** рев'юер, що хоче прогнати кілька агентів по одному PR одночасно й порівняти
їхні знахідки пліч-о-пліч, а не запускати їх по одному й тримати різницю в голові.

**Проблема:** паралельне виконання кількох агентів уже існує (`POST /pulls/:id/review`
з `{all:true}` → `run-executor.ts`, ізоляція збоїв поагентно), але немає сутності,
що зв'язує ці окремі `agent_runs` в один порівнюваний «мультизапуск». Таблиця
`multi_agent_runs` існує як заглушка (`server/src/db/schema/runs.ts:87-96` — лише
`id`, `workspaceId`, `prId`, `ranAt`); ніхто в неї не пише й не читає. Немає й
обчислення «де агенти не згодні» (конфлікти по одному й тому ж місці коду). Контракт
відповіді (`MultiAgentRun`, `AgentColumn`, `Conflict`, `ConflictTake`) уже описаний
у `observability.ts`, але не наповнюється.

## Goals / Non-goals

**Goals:**
- G-1. Роут запуску мультизапуску: створює запис `multi_agent_runs`, лінкує до нього
  окремі `agent_runs` для набору обраних агентів, і повторно використовує наявний
  фоновий `run-executor` (паралельний fan-out, ізоляція збоїв). Повертає ідентифікатор
  мультизапуску + перелік `runId`, щоб клієнт одразу підписався на SSE.
- G-2. Роут читання мультизапуску: віддає `MultiAgentRun` (колонки поагентно зі
  статусом/скором/вартістю/знахідками + персистовані конфлікти).
- G-3. Крос-агентна група «Where agents disagree» обчислюється **on-read** у роуті
  читання з наявних `agent_runs`+`findings`, поверх правила зіставлення знахідок
  (той самий файл + перетин діапазону рядків — рішення D-3; семантична близькість
  НЕ застосовується). Групи **НЕ персистяться** (рішення D-2) — обчислення чисте,
  детерміноване й дешеве (знахідок на PR мало).
- G-4. Атрибуція кожної знахідки до її агента та «did not flag» (агент прогнав, але
  не позначив це місце) зберігаються в даних — сирий матеріал для майбутнього
  Per-Agent Stats.
- G-5. Оцінка перед запуском (pre-run estimate): роут, що повертає поагентні
  час/вартість = середнє останніх N успішних запусків цього агента; агрегат
  час = MAX, вартість = SUM (за узгодженим рішенням продукт-овнера).

**Non-goals:**
- N-1. Будь-яка зміна `ci/` чи `agent-runner/`.
- N-2. Нове паралельне виконання — воно вже є в `run-executor.ts`; повторно
  використовуємо, не переписуємо.
- N-3. Правило зіставлення знахідок — використовуємо наявний line-range примітив
  (`rangeIntersects` у `reviewer-core/src/grounding.ts`); новий алгоритм не винаходимо.
  Семантична близькість / embedder у групуванні НЕ використовується (рішення D-3).
- N-4. Бекенди для Learn / Turn into eval case / Reply to author — вони заглушки на
  клієнті (SPEC-06), сервер їх не реалізує.
- N-5. Per-Agent Stats-роут (`GET /agents/:id/stats`) — окрема майбутня робота; тут
  лише зберігаємо атрибуцію, що його потім живитиме.
- N-6. SSE/RunTrace-механіка — уже існує (`GET /runs/:id/events`, `GET /runs/:id/trace`),
  повторно використовується без змін.

## User stories
- US-1: Як рев'юер, я хочу одним запитом запустити обраний набір агентів по PR, щоб
  вони прогналися паралельно й були зв'язані в один порівнюваний прогін.
- US-2: Як рев'юер, я хочу отримати результат мультизапуску як колонки поагентно, щоб
  бачити статус, скор, вартість і знахідки кожного агента поруч.
- US-3: Як рев'юер, я хочу бачити персистований блок «де агенти не згодні», щоб
  дублі не набридали, а розбіжності ставали видимими.
- US-4: Як рев'юер, я хочу оцінку часу/вартості перед запуском, щоб розуміти ціну
  fan-out до того, як натисну «Run».
- US-5: Як автор фічі Per-Agent Stats (майбутнє), я хочу, щоб атрибуція «хто що
  позначив / не позначив» лишалась у даних, щоб потім її агрегувати.

## Acceptance criteria (EARS)

### Запуск мультизапуску
- AC-1: КОЛИ надходить `POST /pulls/:id/multi-agent-run` з непорожнім набором
  `agent_ids`, система повинна створити один рядок `multi_agent_runs`
  (з `workspaceId`, `prId`, `ranAt`) і повернути його `id` разом із переліком
  створених `runId` для кожного обраного агента.
- AC-2: КОЛИ мультизапуск створено, система повинна створити по одному `agent_runs`
  на кожного обраного агента ще до старту фонового виконання (як це вже робить
  наявний потік `runReview`), щоб клієнт міг підписатися на SSE до/під час прогону.
- AC-3: КОЛИ мультизапуск створено, система повинна зв'язати кожен `agent_runs`
  цього набору з рядком `multi_agent_runs` (лінкування — див. рішення D-1).
- AC-4: КОЛИ фонове виконання стартує, система повинна повторно використати наявний
  `ReviewRunExecutor.executeRuns` (паралельний fan-out, ізоляція збоїв поагентно),
  не запроваджуючи окремий рушій виконання.
- AC-5: ЯКЩО у тілі запиту `agent_ids` порожній або відсутній, ТОДІ система повинна
  відхилити запит із 422 (schema-first zod `body`), не створюючи мультизапуск.
- AC-6: ЯКЩО хоч один `agent_id` не існує / не належить робочому простору, ТОДІ
  система повинна відхилити запит із помилкою й не створювати частковий мультизапуск.
- AC-7: Система повинна обмежувати `POST /pulls/:id/multi-agent-run` тим самим за
  суворістю per-route rate-limit, що й `POST /pulls/:id/review` (кожен виклик — це
  дорогий fan-out LLM-запусків).

### Обчислення групи розбіжностей (on-read, без персисту)
- AC-8: КОЛИ надходить читання мультизапуску, система повинна обчислити крос-агентні
  групи знахідок **на льоту** з наявних `agent_runs`+`findings` цього мультизапуску,
  за правилом зіставлення **той самий файл + перетин діапазону рядків**
  (`rangeIntersects` з `reviewer-core/src/grounding.ts`; семантична близькість НЕ
  застосовується — рішення D-3). Групи **НЕ персистяться** (рішення D-2): обчислення
  чисте й детерміноване, повторюється на кожне читання.
- AC-9: Для кожної групи система повинна вивести по одному запису на кожного агента
  мультизапуску: або вердикт/severity + короткий rationale, якщо агент позначив це
  місце, або маркер «did not flag», якщо агент прогнав (`status='done'`), але це місце
  не позначив.
- AC-10: ЯКЩО агент завершився збоєм/скасуванням (не дав знахідок), ТОДІ система
  повинна не показувати його як «did not flag» (він не давав вердикту взагалі); цей
  стан відрізняється в результаті від справжнього «did not flag».
- AC-11: Система повинна позначити групу як «конфлікт» тоді й лише тоді, коли принаймні
  один агент позначив місце, а принаймні один інший (що теж прогнав, `status='done'`)
  не позначив, АБО коли агенти виставили різні severity на це місце.
- AC-12: Обчислення груп детерміноване: повторне читання тих самих даних дає той самий
  результат. (Персисту немає — джерело правди це `findings`, групи щоразу похідні.)

### Читання мультизапуску
- AC-13: КОЛИ надходить `GET /pulls/:id/multi-agent` (останній мультизапуск для PR),
  система повинна повернути `MultiAgentRun` з `columns` (по одній на агента) і
  `conflicts` (групи, обчислені on-read за AC-8).
- AC-14: Кожна `AgentColumn` повинна містити `run_id`, `agent_id`, `agent_name`,
  `provider`, `model`, `status` (`done|failed|running`), `verdict`, `score`, `summary`,
  `duration_ms`, `cost_usd` та `findings[]` (підмножина полів знахідки: `id`,
  `severity`, `category`, `title`, `file`, `start_line`, `kind`).
- AC-15: Система повинна віддавати `total_duration_ms` як MAX тривалостей колонок
  (паралель) і `total_cost_usd` як SUM вартостей колонок (SUM ігнорує `null`-вартості
  збійних запусків).
- AC-16: ПОКИ хоч один `agent_runs` мультизапуску має статус `running`, система повинна
  віддавати відповідні колонки зі `status: 'running'` (частковий результат читомий,
  без 404); `conflicts` обчислюються лише зі знахідок уже завершених (`done`) прогонів
  — агенти, що ще біжать, у групи поки не додають нічого (група стане повною після їх
  завершення на наступному читанні).
- AC-17: ЯКЩО мультизапуск/PR за вказаним id не існує, ТОДІ система повинна відповісти
  404 (`NotFoundError`), а не порожнім тілом.
- AC-18: ДЕ передано конкретний `:multiRunId` (`GET /pulls/:id/multi-agent/:multiRunId`),
  система повинна повернути саме той мультизапуск, а не останній.

### Оцінка перед запуском
- AC-19: КОЛИ надходить запит на pre-run оцінку для набору `agent_ids`, система повинна
  повернути поагентні `time`/`cost` = середнє останніх **N=5** успішних (`status='done'`)
  запусків цього агента (рішення D-4). Роут — окремий `GET /agents/estimates?ids=…`
  (рішення D-6).
- AC-20: ЯКЩО в агента немає жодного успішного запуску в історії, ТОДІ система повинна
  повернути для нього `null` (час і вартість), а не 0 і не вигадане число.
- AC-21: КОЛИ обчислюється агрегат по набору, система повинна віддати агрегатний час =
  MAX поагентних часів наявних в історії агентів і агрегатну вартість = SUM їхніх
  вартостей, обчислюючи агрегат лише з тих агентів, що мають історію.
- AC-22: ЯКЩО хоч один обраний агент не має історії, ТОДІ система повинна позначити
  оцінку як часткову (`partial: true`), щоб клієнт міг це показати.

### Спільне
- AC-23: Усі нові роути повинні бути scoped робочим простором через наявний
  `getContext(container, req)` і ніколи не повертати дані іншого workspace.
- AC-24: Нові роути повинні бути schema-first: `params`/`body` через zod
  (`fastify-type-provider-zod`), відхиляючи некоректний ввід 422 до входу в handler.
- AC-25: Бізнес-логіка мультизапуску (сервіс) не повинна містити типів Fastify/Drizzle;
  доступ до БД — лише через repository, адаптери — лише через DI-контейнер
  (onion-архітектура, `server/CLAUDE.md`).

## Edge cases
- EC-1: Порожній набір агентів на запуск → 422 (AC-5).
- EC-2: Один агент у наборі — валідний «мультизапуск» з однієї колонки; блок
  розбіжностей тоді завжди порожній (нема з ким конфліктувати).
- EC-3: Усі агенти набору завершились збоєм → `columns` усі `failed`, `conflicts` = `[]`
  (нема знахідок для зіставлення), читання не падає.
- EC-4: Частина агентів ще `running` під час читання → частковий результат, `conflicts`
  порожні до завершення (AC-16).
- EC-5: Два агенти позначили те саме місце з однаковою severity → група існує, але це
  НЕ конфлікт (одностайні); у режимі «тільки конфлікти» вона ховається (клієнт, SPEC-06).
- EC-6: Знахідки з діапазоном рядків (напр. `61-74`) vs одиночний рядок на тому ж файлі
  — зіставлення за перетином діапазону (наявне правило line-range), не за точним рядком.
- EC-7: PR без жодного успішного запуску жодного агента → pre-run оцінка часткова/порожня,
  усі поагентні значення `null` (AC-20, AC-22).
- EC-8: Скасування мультизапуску (через наявний `POST /runs/:id/cancel` для кожного
  runId) → скасовані запуски не рахуються як «did not flag» (AC-10).
- EC-9: Повторний запуск того самого набору по тому ж PR → новий рядок
  `multi_agent_runs`; `GET /pulls/:id/multi-agent` повертає найновіший (AC-13, AC-18
  для доступу до попереднього за id).
- EC-10: Читання під час завершення останнього агента → групи рахуються зі знахідок
  уже `done`-прогонів; агент, що ще біжить, у групи не додає нічого, і наступне читання
  після його завершення дає повну групу (AC-16). Гонок персисту немає — персисту немає.

## Non-functional requirements
- **Продуктивність:** обчислення груп — O(знахідок²) у межах одного мультизапуску;
  прийнятно, бо кількість знахідок на PR невелика. Зіставлення суто детерміноване
  (file + line-range overlap), без викликів embedder — жодних додаткових LLM/мережевих
  витрат на групування (рішення D-3).
- **Надійність / ізоляція:** збій одного агента не валить мультизапуск (успадковується
  від наявного `run-executor`); on-read обчислення груп — чиста функція над уже
  збереженими знахідками, тож окремого стану, який міг би зіпсуватись, немає.
- **Rate limit:** `POST /pulls/:id/multi-agent-run` — той самий за суворістю ліміт, що й
  `/pulls/:id/review` (AC-7).
- **Спостережуваність:** старт/завершення мультизапуску та факт обчислення груп мають
  логуватися структуровано (pino), як і решта потоку review.
- **Безпека:** усі роути scoped workspace (AC-23); тіло PR та тексти знахідок — уже
  недовірені й обробляються наявним пайплайном; нових зовнішніх входів фіча не додає.
- **Retention/приватність:** мультизапуск живе, доки живе PR (каскадне видалення за
  `prId`, як у стубі таблиці). Групи розбіжностей не зберігаються окремо — вони похідні
  від `findings`. PII не додає.

## Inputs and provenance
- `agent_ids` набір, `:id` PR — з тіла/params запиту клієнта (SPEC-06). **Недовірені** —
  валідуються zod + перевіркою належності workspace.
- Знахідки, вердикти, severity, score, вартість, тривалість — з наявних
  `agent_runs`/`reviews`/`findings`, які пише `run-executor` (внутрішнє джерело правди).
- Історія для pre-run оцінки — з наявних `agent_runs` (`status='done'`,
  `durationMs`, `costUsd`) цього агента.
- Правило зіставлення: примітив line-range з `reviewer-core/src/grounding.ts`
  (`rangeIntersects`), той самий файл + перетин діапазону (рішення D-3; без embedder).

## Untrusted inputs
- `agent_ids`, `:id` PR, будь-який `:multiRunId` — валідація zod (типи/формат) +
  авторизаційна перевірка належності workspace (AC-6, AC-23). Некоректні → 422/404,
  ніколи не створювати частковий мультизапуск.
- Тексти знахідок/rationale, що потрапляють у групи, походять з LLM (недовірені),
  але лише зберігаються й віддаються як дані; сервер їх не інтерпретує й не виконує.

## Decisions (закриті продукт-овнером)
- **D-1 (лінкування):** nullable FK `multi_agent_run_id` на `agent_runs` (простий
  індексований one-to-many). Міграція через `pnpm db:generate` (не редагувати
  `migrations/*` вручну).
- **D-2 (групи on-read, без персисту):** «Where agents disagree» обчислюється на
  кожне читання з `agent_runs`+`findings`; НЕ зберігається (ні jsonb, ні таблиці).
  Спрощення: не треба ловити момент завершення мультизапуску, немає міграції під
  конфлікти, ідемпотентності чи гонок. Атрибуція для майбутнього Per-Agent Stats не
  втрачається — вона лежить у `agent_runs`+`findings`, групи завжди перевиводяться.
- **D-3 (правило зіставлення):** той самий файл + перетин діапазону рядків
  (`rangeIntersects`). Семантична близькість/embedder НЕ застосовується — свідоме
  спрощення проти початкового «+ схожість суті» у вимогах.
- **D-4 (N для pre-run):** N = 5 останніх успішних (`status='done'`) запусків агента.
- **D-5 (контракт узгоджено з on-read):** групи НЕ персистяться (див. D-2), тож
  коментар у `observability.ts` про `Conflict` «computed on-read… not stored» є
  правильним і залишається як є. (Ранній чернетковий варіант D-5 казав протилежне —
  «персистуються»; він суперечив D-2 і скасований: домінує D-2.)
- **D-6 (роут pre-run):** окремий легкий роут `GET /agents/estimates?ids=...`.
- **D-7 (історія мультизапусків — ДОДАНО):** новий роут `GET /multi-agent-runs`
  (workspace-scoped, найновіші перші, опційний фільтр `?prId=`) повертає список
  summary-записів (`id`, `pr_id`, `pr_number`, `pr_title`, `ran_at`, `agent_count`,

  `MultiAgentRunSummary` додається server-first → дзеркалиться в client.
