# Spec: Export to CI — серверний модуль `ci` (генерація бандла + інсталяції + CI-прогони)
Spec ID: SPEC-05
Status: draft
Supersedes: —

## Affected packages
- **`server/`** — первинний пакет: новий модуль `server/src/modules/ci/`
  (`routes.ts`/`service.ts`/`repository.ts`), зареєстрований у
  `server/src/modules/index.ts`. Генерація файлів, персистенція інсталяцій і
  читання CI-прогонів живуть тут (запис/ingest `ci_runs` — поза scope, D-6).
- **`client/`** — споживач цього API; описаний окремо у
  [`specs/client/SPEC-06-export-to-ci-ui.md`](../client/SPEC-06-export-to-ci-ui.md).
- **`agent-runner/`** — **зовнішня незмінна залежність** (scope decision #3): цей
  модуль лише генерує файли, що покликаються на вже зібраний рунер. Жодних змін у
  `agent-runner/` ця специфікація не вводить. (Читання артефакту, який рунер
  пише, — поза межами цієї ітерації, див. D-6.)
- **`reviewer-core/`** — не торкається (двигун поза межами, scope decision #3).
- **`vendor/shared`** — контракти CI **вже існують** у
  `server/src/vendor/shared/contracts/eval-ci.ts` (`CiTarget`, `CiFile`,
  `CiExportInput`, `CiExport`, `CiInstallation`, `CiRun`, `CiRunStatus`,
  `AgentManifest`, `CiResultArtifact`) і **вже віддзеркалені** в
  `client/src/vendor/shared/contracts/eval-ci.ts`. Нового контракту в загальному
  випадку вводити не потрібно; будь-яке доповнення йде **спочатку** в серверну
  копію (правило drift з кореневого `CLAUDE.md`).

## Проблема й користувач
**Хто:** автор ревʼю-агента у Studio, який довів агента до готовності й хоче, щоб
той автоматично ревʼював PR у чужому репозиторії через GitHub Actions — без
підтримки сервера DevDigest у рантаймі.

**Проблема:** рунер (`agent-runner/`), схема БД (`ci_installations`, `ci_runs`,
`agents.ci_fail_on`) і всі Zod-контракти CI **вже існують**, але **немає жодного
серверного модуля, який їх зшиває**: ніщо не генерує бандл файлів
(`.devdigest/agents/<slug>.yaml` + `.devdigest/skills/*.md` + workflow +
рунер-бандл) і не персистить факт розгортання агента в репозиторій. `agent-runner`
навіть посилається в коментарях на неіснуючий `server/src/modules/ci/manifest.ts`
(`agent-runner/src/manifest.ts:9`). Ця специфікація закриває серверну діру для
**генерації бандла + персистенції інсталяцій**. Наповнення `ci_runs`
(ingest результатів CI-прогонів) — **поза межами цієї ітерації** (D-6): таблиця
`ci_runs` лишається доступною лише для читання над наявними/seed-даними.

## Goals / Non-goals

**Goals:**
- G-1. Новий модуль `ci` генерує детермінований бандл файлів для цілі **GitHub
  Actions** з наявного агента + його навичок, узгоджений з контрактом
  `AgentManifest`, який `agent-runner` читає без змін.
- G-2. Згенерований workflow викликає **фактичний** рунер
  (`node .devdigest/runner/index.js`, без сабкоманд/`--agent`) з правильними
  env-змінними, а не форму з мокапу; **рунер-бандл включено** в набір файлів,
  `.devdigest/memory.jsonl` — **виключено** (рунер його не читає) — рішення
  D-2/D-3.
- G-3. Персистенція факту розгортання: рядок `ci_installations` на пару
  агент↔репозиторій (реюз наявної таблиці, без нової міграції).
- G-4. Ендпоінт списку CI-прогонів (`ci_runs`) для статус-пілюль CI-таба й
  сторінки CI Runs — **лише читання** над наявними рядками; сама фіча `ci_runs`
  **не наповнює** (ingest поза scope, D-6). Статус-пілюлі можуть бути порожні.
- G-5. Ендпоінти для: експорту (`POST /agents/:id/export-ci`), списку інсталяцій
  агента, списку CI-прогонів, і зміни `Fail CI on` (severity-поріг).

**Non-goals:**
- N-1. Будь-яка **write-інтеграція з GitHub** (відкриття PR із файлами) — scope
  decision #2. `action: "open_pr"` — заглушка: приймається, але повертає
  `pr_url: null` і нічого в GitHub не пише. Реальний шлях — `action: "files"`.
- N-2. Цілі CircleCI / Jenkins / Generic CLI — scope decision #1. Приймається
  тільки `target: "gha"`; інші відхиляються як «не реалізовано».
- N-3. Будь-яка зміна двигуна виконання — `agent-runner/`, `reviewer-core/`, сам
  прохід ревʼю (scope decision #3). Модуль лише генерує конфіг і читає результат.
- N-4. Нова міграція БД — таблиці `ci_installations`/`ci_runs` та
  `agents.ci_fail_on` вже існують (див. AC-11, «Прийняті рішення» D-1). Wizard-вибір
  (`triggers`/`post_as`/`base`) per-installation **не персиститься** (D-1):
  джерело правди після інсталяції — checked-in файли в цільовому репо.
- N-5. Автоматичне виконання CI-прогонів сервером — прогони запускає чужий GitHub
  Actions.
- N-6. **Ingest результатів CI-прогонів у `ci_runs`** (читання
  `devdigest-result.json` з GitHub Actions чи прийом його через ендпоінт) —
  **поза межами цієї ітерації** (D-6). Модуль не пише в `ci_runs`; списки/пілюлі
  читають лише наявні рядки.

## User stories
- **US-1.** Як автор агента, я хочу одним запитом отримати повний набір файлів,
  готових до коміту в цільовий репозиторій, щоб агент запускався на його PR.
- **US-2.** Як автор агента, я хочу, щоб факт розгортання зберігся, щоб CI-таб
  показував, у скількох репозиторіях агент активний.
- **US-3.** Як автор агента, я хочу керувати порогом `Fail CI on`, щоб визначати,
  коли CI має падати (exit non-zero) і блокувати мердж.
- **US-4.** Як користувач, я хочу бачити історію CI-прогонів (репо, агент, подія,
  статус, серйозність, час), щоб моніторити, як ревʼю поводиться в CI.

## Acceptance criteria (EARS)

### Модуль і межі
- **AC-1** (Ubiquitous). Система повинна містити новий модуль
  `server/src/modules/ci/` як один Fastify-плагін
  (`routes.ts`/`service.ts`/`repository.ts`), статично зареєстрований у
  `server/src/modules/index.ts` (конвенція `server/CLAUDE.md`: «one module = one
  Fastify plugin»).
- **AC-2** (Ubiquitous). Усі зовнішні залежності (GitHub-клієнт для читання
  прогонів, доступ до БД, доступ до бандла рунера) система повинна отримувати
  через DI-контейнер (`platform/container.ts`), ніколи не конструюючи адаптер
  усередині сервісу (`server/CLAUDE.md`, onion-architecture).
- **AC-3** (Ubiquitous). Сервіс генерації (`service.ts`) повинен лишатися вільним
  від типів Fastify/Drizzle: він приймає доменні дані й повертає доменний
  `CiExport`, а робота з `request`/`reply` і БД — у `routes.ts`/`repository.ts`
  (onion-architecture, dependency-direction).

### Генерація бандла
- **AC-4** (Event-driven). КОЛИ надходить `POST /agents/:id/export-ci` з валідним
  тілом `CiExportInput`, система повинна повернути `CiExport`
  (`{ installation, files: CiFile[], pr_url }`), де `files` — повний бандл для
  цілі GitHub Actions.
- **AC-5** (Ubiquitous). `files` повинні містити маніфест
  `.devdigest/agents/<slug>.yaml`, чий YAML при парсингу проходить
  `AgentManifest.safeParse` без помилок; поля `name`/`provider`/`model`/
  `system_prompt`/`strategy`/`ci_fail_on` беруться з рядка агента, а `skills` —
  масив **slug-ів** привʼязаних навичок у порядку `agent_skills.order`
  (`eval-ci.ts:231`, узгоджено з `agent-runner/src/manifest.ts`).
- **AC-6** (Ubiquitous). `files` повинні містити по одному
  `.devdigest/skills/<slug>.md` на кожну привʼязану навичку з **розвʼязаним
  тілом** навички (не посиланням), де `<slug>` збігається зі slug-ом у масиві
  `skills` маніфесту (`agent-runner/src/skills.ts:18`).
- **AC-7** (Ubiquitous). `files` повинні містити workflow
  `.github/workflows/devdigest-review.yml`, у якому `on.pull_request.types`
  дорівнює масиву `triggers` із запиту, `runs-on: ubuntu-latest`, кроки
  `actions/checkout@v4` + `actions/setup-node@v4` (node 20), а крок запуску
  викликає **фактичний рунер** — `node .devdigest/runner/index.js` (без
  сабкоманд/`--agent`; slug читається з єдиного маніфесту + env) — а НЕ форму з
  мокапу `.devdigest/runner.mjs review --agent <slug>` (рішення D-2).
- **AC-8** (Ubiquitous). Крок запуску workflow повинен передавати рунеру env
  згідно з `agent-runner/README.md`: `OPENROUTER_API_KEY` і (коли `post_as ≠
  none`) `GITHUB_TOKEN` з `secrets.*`, `GITHUB_REPOSITORY`, `PR_NUMBER`
  (з `pull_request.number`), і `DEVDIGEST_POST_AS`, що дорівнює `post_as` із
  запиту.
- **AC-9** (Ubiquitous). `files` повинні містити зібраний бандл рунера
  `.devdigest/runner/index.js` (файл, який workflow фактично виконує), бо без
  нього цільовий репозиторій не запуститься (`agent-runner/README.md`); і
  **не повинні** містити `.devdigest/memory.jsonl`, бо фактичний рунер його не
  читає (`agent-runner/src` не має жодного `memory`/`jsonl`) — рішення D-3. Це
  свідомо коригує набір із мокапу 02.
- **AC-10** (Ubiquitous). Кожен елемент `files` повинен відповідати контракту
  `CiFile` (`{ path, contents, editable }`), а `path` — бути відносним,
  нормалізованим і без `..`/абсолютних сегментів (безпека шляхів).
- **AC-11** (Event-driven). КОЛИ ціль — `gha` і `action: "files"`, система повинна
  **персистити** інсталяцію: upsert рядка `ci_installations`
  (`agent_id`, `repo`, `target_type='gha'`, `installed_at`) так, щоб повторний
  експорт того самого агента в той самий репозиторій **не створював дубль**, а
  оновлював наявний запис.

### Обмеження цілей та дій (scope)
- **AC-12** (Unwanted behavior). ЯКЩО `target ≠ "gha"`, ТОДІ система повинна
  відхилити запит зрозумілою помилкою «не реалізовано» (4xx), не генеруючи
  файлів і не персистячи інсталяцію (scope decision #1).
- **AC-13** (Optional feature). ДЕ `action: "open_pr"`, система повинна повернути
  `pr_url: null` і **не** виконувати жодного запису в GitHub (заглушка, scope
  decision #2); функціональний шлях — `action: "files"`.
- **AC-14** (Ubiquitous). Валідація тіла повинна бути schema-first через
  `CiExportInput` (`fastify-type-provider-zod`), відхиляючи невалідний ввід 422
  до входу в хендлер (`server/CLAUDE.md`), без ручного `Schema.parse`.

### Інсталяції та `Fail CI on`
- **AC-15** (Event-driven). КОЛИ надходить запит списку інсталяцій агента
  (напр. `GET /agents/:id/ci`), система повинна повернути перелік інсталяцій
  агента, кожну зі **статусом останнього CI-прогону** для цього репозиторію
  (для пілюль CI-таба й лічильника «Active in N repos»).
- **AC-16** (Ubiquitous). Поріг `Fail CI on` повинен зберігатися в
  `agents.ci_fail_on` (`never`/`critical`/`warning`/`any`) — **на рівні агента**,
  спільний для всіх його інсталяцій — і саме з нього деривується `ci_fail_on`
  згенерованого маніфесту (AC-5). Зміна порогу відбувається **наявним
  `PATCH`-шляхом модуля `agents`** (модуль `ci` власного ендпоінта для цього не
  вводить) — рішення D-4.

### CI-прогони (моніторинг, лише читання)
- **AC-17** (Event-driven). КОЛИ надходить запит списку CI-прогонів
  (напр. `GET /ci/runs`), система повинна повернути перелік рядків `CiRun` у
  межах поточного воркспейсу, відсортований за спаданням `ran_at`, з полями репо
  (через `ci_installation_id`), агента, статусу, кількості знахідок, вартості й
  часу — читаючи **лише наявні** рядки `ci_runs`; за відсутності рядків повертає
  порожній список (не помилку).
- **AC-18** (Ubiquitous). Ця ітерація **не наповнює** `ci_runs`: модуль `ci`
  **не повинен** ані писати в `ci_runs`, ані виставляти ingest-ендпоінт
  (напр. `POST /ci/runs`) чи read-only «refresh» із GitHub Actions (рішення D-6).
  Статус-пілюлі інсталяцій (AC-15) і список CI Runs (AC-17) деривуються виключно
  з рядків, що вже існують у таблиці (напр. seed-даних).
- **AC-19** (State-driven). ПОКИ для інсталяції немає жодного рядка `ci_runs`,
  система повинна повертати цю інсталяцію без статус-пілюлі (нейтральний
  «ще не запускалось»), а не вигадувати `succeeded`.

### Безпека
- **AC-20** (Ubiquitous). Рядок `repo` (`"owner/name"`) — **недовірений ввід**;
  система повинна валідувати його формат перед використанням у шляхах/URL і
  ніколи не інтерполювати сирим у shell чи файловий шлях (injection/шлях-траверс).
- **AC-21** (Ubiquitous). Згенеровані файли **не повинні містити значень
  секретів**: маніфест і workflow посилаються на `OPENROUTER_API_KEY`/
  `GITHUB_TOKEN` лише як на `secrets.*`/`env` цільового репозиторію; жоден ключ
  зі Studio (`LocalSecretsProvider`) не потрапляє в `contents` (A09, і
  `agent-runner/CLAUDE.md`).
- **AC-22** (Unwanted behavior). ЯКЩО агент `:id` не належить воркспейсу
  запитувача, ТОДІ будь-який з ендпоінтів (експорт, список, зміна порогу) повинен
  повернути 404/403 і не розкривати існування агента (A01, workspace-scoping —
  як `agents`/`skills` модулі).

## Edge cases
- **EC-1.** Агент без привʼязаних навичок → маніфест із `skills: []`, жодного
  `.devdigest/skills/*.md`; бандл валідний (AgentManifest толерує порожній
  `skills`, `eval-ci.ts:239`).
- **EC-2.** Повторний експорт того самого агента в той самий репо → інсталяція
  оновлюється, не дублюється (AC-11); файли перегенеровуються за поточним станом
  агента.
- **EC-3.** `triggers: []` у запиті → `.default(['opened','synchronize',
  'reopened'])` контракту вже підставляє дефолт; порожній масив після дефолту не
  виникає, але workflow повинен лишатися валідним YAML навіть за одного тригера.
- **EC-4.** Slug навички містить символи, небезпечні для імені файлу → шлях
  `.devdigest/skills/<slug>.md` повинен бути санітизований/відхилений (AC-10),
  бо той самий slug читає рунер.
- **EC-5.** `system_prompt` агента містить YAML-спецсимволи/багаторядковість →
  серіалізація маніфесту повинна коректно екранувати (використати YAML-серіалайзер,
  не ручну конкатенацію), щоб рунерів `parseYaml` + `AgentManifest.safeParse`
  пройшли (дзеркало до `agent-runner/src/manifest.ts:62-69`).
- **EC-6.** `action: "open_pr"` (заглушка) → `pr_url: null`, інсталяція **не**
  персиститься, бо реального розгортання не сталося; persist лише для
  `action: "files"` (AC-11, рішення D-5).
- **EC-7.** `ci_installation_id` у наявному рядку `ci_runs` = `null` (інсталяцію
  видалили, `onDelete: 'set null'`) → прогін лишається в списку CI Runs, але без
  привʼязки до репо (AC-17 має толерувати null).
- **EC-8.** Ціль `gha`, але цільовий репо приватний/невідомий Studio → генерація
  файлів **не залежить** від доступу до GitHub (файли — чистий рендер), тож успіх
  генерації не блокується недоступністю репо (для `action:"files"` мережа не
  задіяна взагалі).

## Non-functional requirements
- **NFR-1 (Продуктивність).** Генерація бандла — суто CPU-операція над уже
  завантаженими даними агента/навичок; жодних викликів моделі й (для
  `action:"files"`) жодних мережевих викликів. Один `POST` = один
  згенерований бандл.
- **NFR-2 (Безпека).** Див. AC-20..AC-22: недовірений `repo`, відсутність
  секретів у файлах, workspace-scoping. Додатково: `contents` згенерованих файлів
  містять `system_prompt` і тіла навичок — це дані, які автор агента ввів сам
  (не зовнішній зловмисник), але вони лишаються **plain text** у файлах, без
  виконання.
- **NFR-3 (Надійність/ідемпотентність).** Повторний експорт ідемпотентний за
  інсталяцією (AC-11 upsert) — повторний експорт того самого агента в той самий
  репо не множить рядки `ci_installations`.
- **NFR-4 (Спостережуваність).** Кожен експорт логується структуровано (агент,
  репо, ціль, дія, кількість файлів) — джерело правди для дебагу CI-таба.
- **NFR-5 (Сумісність контрактів).** Згенерований маніфест валідується **тією
  самою** Zod-схемою `AgentManifest`, що й у `agent-runner`, — жодної
  паралельної/ручної форми, щоб формат не розʼїхався
  (`eval-ci.ts`, `agent-runner/src/manifest.ts`). (Схема `CiResultArtifact`
  лишається спільним контрактом для майбутнього ingest, D-6, але цією ітерацією
  на сервері не використовується.)

1. **`repo` (`"owner/name"`)** — валідувати формат (regex `owner/name`), не
   інтерполювати сирим у shell/шлях (AC-20).
2. **Slug-и навичок** у шляхах файлів — санітизувати/валідувати (AC-10, EC-4).

> Примітка: `CiResultArtifact` із чужого CI — недовірений вхід, але його прийом
> (ingest) **поза межами цієї ітерації** (D-6); коли ingest додаватиметься,
> обовʼязковий `safeParse` перед записом у `ci_runs` стане окремим AC.

## Прийняті рішення
Усі попередні відкриті питання закриті рішеннями користувача (координатора).

- **D-1 (персистенція; без wizard-вибору).** Таблиці `ci_installations`, `ci_runs`
  (`server/src/db/schema/ci.ts`) і колонка `agents.ci_fail_on`
  (`server/src/db/schema/agents.ts:25`) вже існують, як і всі CI-контракти
  (`eval-ci.ts`) — **нова міграція не потрібна**. Wizard-вибір
  `triggers`/`post_as`/`base` per-installation **не персиститься**: джерело правди
  після інсталяції — checked-in файли в цільовому репо; «↻ Update CI config»
  регенерує з дефолтів + поточного стану агента (жодної нової колонки).
- **D-2 (форма виклику рунера — фактична).** Згенерований workflow викликає
  **фактичний** рунер `node .devdigest/runner/index.js` (без сабкоманди/`--agent`;
  slug читається з єдиного маніфесту + env — `agent-runner/README.md`), а не форму
  з мокапу `.devdigest/runner.mjs review --agent <slug>`. Мокап трактується як
  ілюстративний; авторитет — фактичний рунер (незмінна залежність, scope #3).
- **D-3 (склад бандла).** Бандл = маніфест `.devdigest/agents/<slug>.yaml` +
  `.devdigest/skills/<slug>.md`×N + workflow + **рунер-бандл**
  `.devdigest/runner/index.js`. `.devdigest/memory.jsonl` **виключено** — фактичний
  рунер його не читає. Це свідомо коригує набір файлів із мокапу 02.
- **D-4 (зміна `Fail CI on`).** `agents.ci_fail_on` оновлюється **наявним
  `PATCH`-роутом модуля `agents`**; модуль `ci` власного ендпоінта для цього не
  вводить (AC-16).
- **D-5 (persist лише для `files`).** Інсталяція персиститься тільки при
  `action:"files"`; для `action:"open_pr"` (заглушка) реального розгортання не
  сталося, тож рядок `ci_installations` не пишеться (AC-11, EC-6).
- **D-6 (ingest `ci_runs` — поза scope цієї ітерації).** Наповнення `ci_runs`
  (прийом/читання `devdigest-result.json` із GitHub Actions чи через ендпоінт)
  **не реалізується** цією фічею. Модуль `ci` не пише в `ci_runs` і не виставляє
  ingest-ендпоінта. Статус-пілюлі й список CI Runs читають **лише наявні** рядки
  (напр. seed-дані) і коректно рендерять порожній стан (AC-17/AC-18/AC-19).
  Контракт `CiResultArtifact` лишається спільним із рунером для майбутнього
  ingest, але цією ітерацією на сервері не використовується.

## Прийняті припущення
- **A-1 (генерація не залежить від GitHub).** Для `action:"files"` генерація —
  чистий рендер, без мережі; недоступність цільового репо не блокує експорт
  (EC-8).
- **A-2 (мова).** Специфікація — українською; згенеровані файли (YAML/MD/workflow)
  і рядки API — англійською, як решта коду.
